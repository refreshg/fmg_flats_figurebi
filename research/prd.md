## 1. პრობლემა

დეველოპერი ყიდის ბინას, რომელიც ჯერ არ არსებობს. მყიდველი უნდა მიიღოს ხუთნიშნა თანხის გადაწყვეტილება Excel-ის ცხრილისა და რამდენიმე რენდერის საფუძველზე.

**დღევანდელი მდგომარეობა მცირე/საშუალო დეველოპერთან:**
- ხელმისაწვდომობა და ფასები — Excel-ში ან მენეჯერის თავში; საიტზე მოძველებული
- მყიდველი ვერ ხვდება *რომელია* კონკრეტული ბინა კორპუსზე და *რას დაინახავს* ფანჯრიდან
- ყოველი შეკითხვა მოითხოვს მენეჯერის ჩართვას — არ არსებობს self-service
- დეველოპერს არ აქვს მონაცემი, რომელი ბინები იზიდავს ინტერესს გაყიდვამდე

**ალტერნატივები, რომლებიც უკვე არსებობს:** ან იაფი 2D შახმატკა სუსტი buyer experience-ით, ან ძვირი custom 3D build (quote-ზე, 1–5 კვირა, ხშირად $10k+). შუალედი ცარიელია — ეს არის ჩვენი შესაძლებლობა ([patterns.md](patterns.md), პატერნი 2).

## 2. პროდუქტის ხედვა და პოზიციონირება

> **3D-ხარისხის საყიდლელი გამოცდილება, 2D-ის ფასად და onboarding-ის სიჩქარით.**

| განზომილება | 2D ბანაკი | 3D ბანაკი | **FMG Flats** |
|---|---|---|---|
| Buyer experience | სუსტი | ძლიერი | **ძლიერი** |
| ფასი | $299–600/თვე | quote, ხშირად $10k+ build | **$249–449/თვე** |
| Onboarding | 3–5 დღე | 1–5 კვირა | **≤5 სამუშაო დღე** |
| Self-serve | ✅ | ❌ | **✅** |

**როგორ ვაღწევთ:** V1-ში *არ* ვაშენებთ Unreal Engine pipeline-ს. ვიყენებთ **pre-rendered 2.5D მიდგომას** — დეველოპერის არსებული რენდერები + polygon overlay რედაქტორი (Flatris-ის მოდელი) + ფასადზე hover-highlight (YNH-ის მთავარი wow-ეფექტი). ეს იძლევა 3D-ის *აღქმას* 3D-ის *ხარჯის* გარეშე.

## 5. ფუნქციური მოთხოვნები

### 5.1 Core flow (P0)

**FR-1 · გენგეგმა**
დეველოპერის მიერ ატვირთულ მასტერპლანის სურათზე კორპუსები მონიშნულია polygon-ებით. Hover → კორპუსის სახელი + ხელმისაწვდომი ერთეულების რაოდენობა. კლიკი → კორპუსის ხედი.
*Acceptance:* მინიმუმ 20 კორპუსი ერთ გენგეგმაზე შესრულების დეგრადაციის გარეშე.

**FR-2 · კორპუსის ხედი**
ფასადის რენდერი polygon-ებით თითო ბინაზე. სტატუსი ფერით (ხელმისაწვდომი / დაჯავშნილი / გაყიდული). რენდერების კარუსელი მრავალი მხრიდან (Flatter-ის მოდელი). Hover → tooltip: ID, მ², ოთახები, ფასი.
*Acceptance:* ≤2 წმ ჩატვირთვა 4G-ზე.

**FR-3 · სართულის ხედი**
ორი გადართვადი რეჟიმი: **(ა) სართულის გეგმა** — 2D გეგმა ბინების კონტურებით; **(ბ) შახმატკა** — ყველა სართული ერთ ბადეში, სტატუსებით. მომხმარებელი თავად ირჩევს.
*Acceptance:* შახმატკა 30 სართული × 8 ბინა იკითხება მობილურზე.

**FR-4 · ბინის ბარათი**
სავალდებულო: ID, სტატუსი, სართული, მ² (საერთო/საცხოვრებელი), ოთახები, ორიენტაცია, ფასი (+ მ²-ზე), გეგმა, გალერეა, PDF, lead form.
*Acceptance:* ბარათს აქვს პირდაპირი URL — გაზიარებადი და SEO-indexable.

### 5.2 Buyer tools (P0)

**FR-5 · ფილტრები** — სართული, ოთახები, ფართი, ფასი, ორიენტაცია, სტატუსი, ტეგები (ბალკონი, ტერასა, ეზო, penthouse). შედეგი real-time, URL-ში აისახება.
**FR-6 · Favourites** — გაზიარებადი ბმულით, რეგისტრაციის გარეშე (localStorage + share token).
**FR-7 · Compare** — 2–4 ბინა გვერდიგვერდ.
**FR-8 · List/Grid ხედი** — ვიზუალურის ალტერნატივა, სორტირებით.

### 5.3 Admin (P0)

**FR-9 · Polygon რედაქტორი** ⭐ *კრიტიკული*
Admin ატვირთავს სურათს და თაგვით ხაზავს კონტურებს, აკავშირებს ერთეულის ჩანაწერთან. **ეს არის მთელი self-serve მოდელის საკვანძო კომპონენტი** — თუ ეს არ იმუშავებს ინტუიციურად, ვბრუნდებით ძვირ manual onboarding-ზე.
*Acceptance:* არატექნიკური მომხმარებელი ხაზავს 50 polygon-ს ≤30 წუთში, ინსტრუქციის გარეშე.

**FR-10 · Inventory მართვა** — ერთეულების CRUD, bulk edit, CSV import/export, Google Sheets sync (იაფი inventory source — Flatris/3DFF-ის მოდელი), custom fields.
**FR-11 · Lead inbox** — შემოსული განაცხადები ბინის კონტექსტით, email შეტყობინება, CSV export.
**FR-12 · ბრენდინგი** — ლოგო, ფერები, შრიფტი, custom domain.

### 5.4 დისტრიბუცია (P0)
**FR-13** — `<iframe>` embed ერთი snippet-ით, responsive
**FR-14** — hosted subdomain `{client}.fmgflats.com` + custom domain, SEO meta, multilanguage (ka/en/ru მინიმუმ)

### 5.5 ანალიტიკა (P1)
**FR-15** — event-level tracking: ბინის ნახვა, დრო, favourite, compare, ფილტრის გამოყენება
**FR-16** — dashboard: top ბინები/კორპუსები, demand ranking, კონვერსია, drop-off flow-ის საფეხურებზე

### 5.6 V2 highlights
**FR-18 · ფასადზე hover-highlight** — ბინაზე hover → ფასადზე ინთება მისი ფანჯრები. მთავარი ვიზუალური დიფერენციატორი.
**FR-19 · Dynamic PDF** — პერსონალიზებული ბროშურა არჩეული ბინით, დეველოპერის ბრენდით.
**FR-20 · Kiosk რეჟიმი** — fullscreen touch, offline-ready, idle attractor. ერთი კოდბაზიდან — მაღალი ROI upsell.

## 8. ტექნიკური მიმართულება

**შემოთავაზება (არ არის საბოლოო):**
- **Frontend:** React + TypeScript; viewer როგორც დამოუკიდებელი embeddable bundle (≤200KB gzipped core)
- **Polygon rendering:** SVG overlay responsive სურათზე — DOM event-ები უფასოდ, accessibility უფასოდ, Canvas-ის სირთულის გარეშე. Canvas-ზე გადავდივართ მხოლოდ თუ >300 polygon ერთ ხედში
- **Backend:** REST/tRPC API; PostgreSQL (პროექტი → კორპუსი → სართული → ერთეული იერარქია); S3-თავსებადი storage + CDN
- **Admin:** ცალკე SPA, საერთო ტიპებით
- **Analytics:** საკუთარი event pipeline (GA4-ზე დამოკიდებულება არა — ad-blocker-ები კლავს მონაცემს)

**გადასაწყვეტი (open questions):**
1. Multi-tenancy — schema-per-tenant vs row-level? (მასშტაბი vs სიმარტივე)
2. სურათების pipeline — ატვირთვისას გენერაცია თუ on-the-fly transform?
3. Polygon კოორდინატები — normalized (0–1) აუცილებელია responsive-ისთვის; როგორ ვმართავთ სხვადასხვა aspect ratio-ს?
4. Offline kiosk — PWA თუ ნატიური wrapper?
